# 한끼잇다(temp-react) 백엔드 연동 안내서

이 문서 하나만 읽으면 이 프로젝트가 무엇인지, 어떻게 실행해보는지, 어떤 API를 만들어서 어떻게 연결해야 하는지 전부 알 수 있도록 정리했습니다. 이 대화의 이전 맥락을 모르는 분이 `temp-react` 폴더만 통째로 받아서 보는 상황을 가정하고 썼습니다.

---

## 0. 프로젝트가 뭔가요

"한끼잇다"는 매장/기관에서 남는 도시락(잉여 식품)을 필요한 사람에게 나눠주는 서비스의 MVP입니다.

- 사용자는 지도에서 매장을 찾아 도시락을 **신청**할 수 있습니다.
- 매장/기관 담당자는 **소속 인증**을 받으면 잉여 식품을 **등록**할 수 있습니다.
- 지금 이 저장소는 **React 프론트엔드만 완성된 상태**이고, 백엔드 서버는 아직 없습니다. 화면과 상호작용 로직은 다 만들어져 있고, 실제 데이터를 주고받을 자리(API 호출)만 비어 있는 상태라고 보면 됩니다.

## 1. 로컬에서 실행해보기

```bash
cd temp-react
npm install
cp .env.example .env   # 그리고 .env 안의 값을 채워주세요 (2번 항목 참고)
npm start
```

브라우저에서 `http://localhost:3000`이 열립니다. **백엔드가 없어도** 로그인 버튼부터 모든 화면 이동까지는 정상적으로 동작합니다. 다만 목록/프로필처럼 서버 데이터가 필요한 부분은 빈 화면이거나 "서버 응답을 해석할 수 없습니다..." 같은 에러 문구가 보이는데, 이는 `REACT_APP_API_BASE_URL`이 실제 서버를 가리키지 않아서 생기는 정상적인 현상입니다.

### 참고: 개발 환경
- Node.js, npm이 설치되어 있어야 합니다 (이 프로젝트는 Node 20+ 에서 확인했습니다).
- 프레임워크는 `react-scripts`(Create React App) 5.0.1, React 19.

## 2. 환경 변수 (.env)

`.env.example`을 복사해서 `.env` 파일을 만들고 아래 두 값을 채워주세요.

```
REACT_APP_API_BASE_URL=http://localhost:8080
REACT_APP_KAKAO_MAP_KEY=발급받은_카카오맵_JavaScript_키
```

- `REACT_APP_API_BASE_URL` — 백엔드 서버 주소입니다(끝에 `/` 없이). 프론트의 모든 API 요청이 이 주소 뒤에 경로를 붙여서 나갑니다. (예: `http://localhost:8080/api/stores`)
- `REACT_APP_KAKAO_MAP_KEY` — 홈 화면 지도를 띄우기 위한 카카오맵 키입니다. 발급 방법은 8번 항목 참고. 이 값이 없으면 지도 자리에 안내 문구만 뜨고 나머지 기능은 정상 동작합니다.

`.env`는 `.gitignore`에 이미 추가되어 있어서 커밋되지 않습니다.

## 5. 인증(로그인) 연동

- 로그인 성공 시 백엔드가 내려주는 **자체 서비스 토큰**을 프론트가 `localStorage`(`hankki_auth_token` 키)에 저장합니다(`src/api/client.js`의 `setAuthToken`, `src/api/auth.js`의 `loginWithKakao`가 자동으로 호출).
- 이후 모든 API 요청에 `Authorization: Bearer <token>` 헤더가 자동으로 붙습니다.
- **주의**: 지금 로그인 화면의 "카카오 로그인" 버튼은 실제 카카오 OAuth 리다이렉트를 하지 않고, 클릭하면 바로 홈 화면으로 이동하는 임시 동작입니다. 실제 연동 시 다음 흐름으로 교체가 필요합니다.
  1. 버튼 클릭 → 카카오 인가 URL로 리다이렉트 (`https://kauth.kakao.com/oauth/authorize?client_id=...&redirect_uri=...&response_type=code`)
  2. 카카오가 `redirect_uri?code=xxx`로 돌아옴
  3. 그 code를 `loginWithKakao(code)`에 넘김 → 내부에서 `POST /api/auth/kakao`를 호출하고, 응답의 `token`을 자동 저장
  4. 홈 화면으로 이동
- 백엔드가 만들어야 할 것: `POST /api/auth/kakao` — body `{ code }` → 카카오 서버와 토큰 교환 + 회원 조회/생성 후 `{ token, isNewUser }` 반환.

## 6. 소속 인증 & 심사(pending) 플로우

매장/기관 담당자가 "식품 등록" 기능을 쓰려면 마이페이지에서 소속 인증을 받아야 합니다. **즉시 승인**과 **관리자 심사** 두 가지 방식을 모두 지원하도록 프론트가 이미 구현되어 있으니, 백엔드 정책에 맞는 쪽으로 응답만 내려주면 됩니다.

`POST /api/verifications` 요청에 대해:

- **즉시 승인하는 서비스라면** → 응답에 `{ verified: true, org, status: "approved" }`를 내려주세요. 프론트는 바로 "인증 완료" 화면을 보여주고 식품 등록 잠금을 풉니다.
- **관리자 심사가 필요한 서비스라면** → 응답에 `{ verified: false, org, status: "pending" }`를 내려주세요. 프론트는 자동으로 "인증 심사 중이에요" 화면과 마이페이지의 "⏳ 심사중" 배지를 보여주고, 식품 등록은 계속 잠긴 상태로 유지합니다.
- 심사가 끝나 관리자가 승인/반려하면, 사용자가 앱을 다시 열거나 마이페이지를 재방문할 때 `GET /api/verifications/me`가 최신 상태(`{ verified, org, status }`, status는 `"none" | "pending" | "approved" | "rejected"`)를 반환하도록 해주세요. **실시간 알림(push)까지는 프론트에 구현되어 있지 않고, 재조회 시점에 반영되는 구조**입니다.
- `status: "rejected"`를 내려주면, 재신청 폼 위에 "이전 신청이 반려되었어요" 안내 문구가 자동으로 표시됩니다.
- 사용자가 인증을 해제하거나 심사 신청을 취소하면 `DELETE /api/verifications/me`가 호출됩니다. 이 요청 후에는 프론트가 무조건 `{ verified: false, status: "none" }`으로 되돌립니다.

## 7. API 명세 (전체 엔드포인트)

모든 응답은 JSON이며, 실패 시 `{ "message": "사람이 읽을 수 있는 에러 메시지" }` 형태를 기대합니다(프론트가 이 `message`를 그대로 alert 등으로 사용자에게 보여줍니다).

### 인증
| Method | Path | Body | Response |
|---|---|---|---|
| POST | `/api/auth/kakao` | `{ code }` | `{ token, isNewUser }` |

### 매장 / 도시락
| Method | Path | Query/Body | Response |
|---|---|---|---|
| GET | `/api/stores` | `?keyword=`(선택) | `[{ id, name, address, lat, lng, hours, phone, photoUrl }]` |
| GET | `/api/stores/:storeId` | - | `{ id, name, address, lat, lng, hours, phone, photoUrl }` |
| GET | `/api/stores/:storeId/lunchbox` | - | `{ registrationId, menuItems: string[], allergyItems: string[], photoUrl }` |
| GET | `/api/stores/mine` | - | `[{ id, name, address, lat, lng, hours, phone, photoUrl }]` (내가 관리하는 매장 목록 — 식품 등록 화면에서 사용) |

`lat`/`lng`는 지도 마커 좌표(위경도)입니다. 주소 → 좌표 변환(지오코딩)은 백엔드에서 매장 등록 시 카카오 로컬 API로 처리하거나, 매장 등록 폼에서 좌표를 직접 입력받는 방식 중 편한 쪽으로 하면 됩니다. 좌표가 없는 매장은 지도에 표시되지 않습니다.

`/api/stores/mine`은 **한 계정이 여러 매장을 관리할 수 있다는 전제**로 배열을 반환합니다. 계정과 매장을 몇 대 몇으로 연결할지(1:1, 1:N)는 백엔드에서 정하면 됩니다 — 예를 들어 소속 인증 시 매장을 하나씩 등록/승인받는 구조로 설계하면 자연스럽게 N개가 쌓입니다. 프론트는 이 목록이 1개면 자동으로 선택하고, 2개 이상이면 등록 화면 상단에 매장을 고르는 탭을 보여줍니다.

### 도시락 신청
| Method | Path | Body | Response |
|---|---|---|---|
| POST | `/api/applications` | `{ storeId, registrationId, pickupTime }` | `{ id, storeId, registrationId, storeName, pickupTime, status, createdAt }` |
| GET | `/api/applications/me` | - | `[{ id, store, date, time, status }]` — status 예: `"수령완료" \| "취소됨" \| "수령대기"` |
| POST | `/api/applications/:applicationId/cancel` | - | - |

`registrationId`는 이 신청이 어떤 잉여 식품 등록건에 대한 것인지 나타냅니다(아래 "등록건별 신청자 관리" 참고). `GET /api/stores/:storeId/lunchbox` 응답의 `registrationId` 값을 그대로 신청 요청에 담아 보냅니다.

### 잉여 식품 등록
| Method | Path | Body | Response |
|---|---|---|---|
| POST | `/api/food-registrations` | `multipart/form-data`: `storeId`, `menuItems[]`(반복), `allergyItems[]`(반복), `quantity`, `photo`(선택) | `{ id, storeId, menu, quantity, date, status }` |
| GET | `/api/food-registrations/me` | - | `[{ id, storeId, menu, quantity, date, status, applicantCount }]` — status 예: `"등록됨" \| "마감됨" \| "수령완료"`, `applicantCount`(선택)는 등록 내역 목록에 "신청 N건"으로 표시됩니다 |

⚠️ 식품 등록은 **소속 인증이 완료된 사용자만** 호출할 수 있어야 합니다. 프론트는 UI에서만 막고 있으므로, 백엔드에서도 반드시 인증 여부를 검사해서 인증 안 된 사용자의 요청은 401/403으로 막아주세요. 여러 매장을 관리하는 계정이라면 요청에 담긴 `storeId`가 실제로 그 계정이 관리하는 매장인지도 검증해주세요.

### 등록건별 신청자 관리 (식품 등록자가 신청을 수락/거절)
| Method | Path | Body | Response |
|---|---|---|---|
| GET | `/api/food-registrations/:registrationId/applicants` | - | `[{ id, applicantName, pickupTime, status }]` — `id`는 application id, status: `"대기중" \| "수락됨" \| "거절됨"` |
| POST | `/api/food-registrations/:registrationId/applicants/:applicationId/respond` | `{ decision: "accept" \| "reject" }` | - |

마이페이지 > 등록 내역에서 등록건을 하나 누르면 "신청자 관리" 화면으로 들어가 이 두 API를 사용합니다. 수락/거절 시 해당 신청자의 `GET /api/applications/me` 상태도 함께 갱신해주세요(신청자 쪽 "신청 내역" 화면에도 반영되어야 하므로).

### 내 프로필

## 8. 카카오맵 연동 방법 (지도 + 검색)

지도는 이미 카카오맵 JavaScript SDK로 완전히 구현되어 있습니다(`src/lib/kakaoMap.js`, `App.js`의 `MapArea` 컴포넌트). 백엔드 개발자가 직접 할 일은 **키 발급과 매장 좌표 데이터를 잘 채워주는 것**뿐입니다.

1. https://developers.kakao.com → 로그인 → "내 애플리케이션" → 애플리케이션 추가
2. "앱 키" 메뉴에서 **JavaScript 키** 복사
3. "플랫폼 > Web 플랫폼 등록"에 서비스 도메인 등록 (로컬 테스트 시 `http://localhost:3000`도 등록)
4. "제품 설정 > 카카오맵" 활성화 확인
5. `.env`의 `REACT_APP_KAKAO_MAP_KEY`에 붙여넣고 `npm start` 재시작

**동작 방식**
- 지도는 기본적으로 부산시청 좌표(35.1796, 129.0756)를 중심으로 뜹니다.
- 홈 화면 진입 시 `GET /api/stores`로 전체 매장 목록을 한 번 불러와 지도에 마커로 표시합니다.
- 검색창에 입력한 검색어는 **이미 불러온 매장 목록을 이름/주소로 프론트에서 필터링**하는 방식입니다(별도 검색 API 호출 없음). 나중에 매장이 많아져 서버 검색이 필요해지면, `fetchStores({ keyword })`가 이미 `?keyword=` 쿼리를 보내도록 되어 있으니 `GET /api/stores?keyword=`만 지원하도록 백엔드를 확장하면 됩니다.
- 마커 클릭 → 해당 매장 정보를 들고 도시락 신청 화면으로 이동 → `GET /api/stores/:storeId/lunchbox` 호출.

## 10. 연동 체크리스트 (이 순서로 진행하면 됩니다)

1. `.env`에 `REACT_APP_API_BASE_URL`을 로컬 백엔드 주소로 설정
2. `GET /api/stores`부터 구현 → 홈 화면 지도에 마커가 뜨는지 확인 (카카오 키도 같이 설정해야 지도 자체가 보입니다)
3. `POST /api/auth/kakao` 구현 + 프론트의 로그인 버튼을 실제 카카오 리다이렉트로 교체 (5번 항목)
4. `GET/PATCH /api/users/me`, `GET /api/users/me/stats` → 마이페이지 프로필/통계 확인
5. `GET/POST/DELETE /api/verifications*` → 소속 인증 플로우 확인 (즉시 승인부터 먼저 테스트해보고, 필요하면 심사 플로우로 전환)
6. `GET /api/stores/:id/lunchbox`, `POST /api/applications`, `GET /api/applications/me` → 도시락 신청 플로우 확인
7. `GET /api/stores/mine`, `POST /api/food-registrations`, `GET /api/food-registrations/me` → 식품 등록 플로우 확인 (소속 인증된 계정으로 테스트, 매장 여러 개 연결해서 선택 탭도 확인)
8. `GET /api/food-registrations/:id/applicants`, `POST .../respond` → 등록 내역에서 신청자 수락/거절 확인
9. `GET/POST/DELETE /api/favorites`, `GET/PATCH /api/users/me/notification-settings`, `POST /api/support/inquiries` → 나머지 마이페이지 기능
10. `POST /api/admin/login`, `GET /api/admin/verifications`, `POST /api/admin/verifications/:id/respond` → `/admin` 경로에서 관리자 로그인 후 인증 승인/반려 확인 (13번 항목)

각 단계마다 프론트 코드 수정 없이, 백엔드가 위 명세대로 응답을 내려주기만 하면 화면에 바로 반영됩니다.

## 11. 알려진 제약 / 다음 단계

- 실제 카카오 로그인 리다이렉트는 아직 프론트에 연결되어 있지 않습니다 (5번 항목).
- 신청/등록 내역, 매장 목록에 페이지네이션이 없습니다 — 지금은 전체 목록을 한 번에 받아온다고 가정합니다. 데이터가 많아지면 추가 필요.
- 매장/프로필 사진은 각각 별도 업로드 API로 분리되어 있습니다 — 백엔드 스토리지 정책(S3 등)에 맞춰 구현하면 됩니다.
- 한 계정이 여러 매장을 관리하는 구조는 지원하지만(`GET /api/stores/mine`), **매장을 새로 추가/등록하는 화면은 아직 없습니다**. 지금은 "이미 계정에 연결된 매장 목록 중 골라서 등록"만 가능하고, 계정↔매장 연결 자체는 백엔드(또는 관리자)가 처리한다고 가정합니다.
- 소속 인증 승인은 이 프론트엔드 안에 관리자 화면이 없습니다 — 자세한 내용은 13번 항목 참고.

## 12. 백엔드 없이 프론트만 먼저 확인하고 싶다면

`.env`를 설정하지 않고 `npm start`만 실행해도 앱은 정상적으로 뜨고 모든 화면 이동이 가능합니다. 목록/프로필은 빈 상태 또는 에러 문구로 보이고, 지도는 안내 문구로 보이는 게 정상입니다(콘솔에 실패 로그만 찍히고 화면은 깨지지 않습니다). `REACT_APP_API_BASE_URL`을 실제 서버 주소로 바꾸는 순간, 코드 수정 없이 화면들이 실 데이터로 채워집니다.

## 13. 소속 인증 승인 — 관리자 화면 (구현 완료)

소속 인증 신청을 검토·승인·반려할 수 있는 **간단한 관리자 화면을 이 프로젝트 안에 이미 만들어뒀습니다.** 일반 사용자 화면(휴대폰 폭 고정 `.app-frame`)과는 분리된, 데스크톱에서 보기 편한 넓은 레이아웃입니다.

### 접속 방법
- 브라우저에서 **`/admin`** 경로로 접속하면 관리자 로그인 화면이 뜹니다. (배포 시 서버가 이 경로도 index.html로 서빙해주기만 하면 됩니다 — 대부분의 정적 호스팅/SPA 배포 설정에 이미 포함되어 있습니다.)
- 또는 일반 로그인 화면 하단의 "관리자이신가요?" 링크로도 들어갈 수 있습니다.
- 로그인에 성공하면 관리자 토큰을 일반 사용자 토큰과는 **별도의 localStorage 키**(`hankki_admin_token`)에 저장하므로, 관리자로 로그인한 상태와 일반 사용자로 로그인한 상태가 서로 섞이지 않습니다.

### 화면 구성
- **관리자 로그인** (`AdminLoginScreen`) — 비밀번호 하나만 입력받는 단순한 로그인 폼입니다.
- **소속 인증 심사** (`AdminVerificationsScreen`) — 대기 중인 인증 신청을 카드 목록으로 보여주고, 각 카드에 신청자 이름/소속명/제출일/첨부 서류 링크(있는 경우)와 "승인"/"반려" 버튼이 있습니다. 승인/반려하면 해당 카드가 목록에서 바로 사라집니다.

### 백엔드가 구현해야 할 API
| Method | Path | Body | Response |
|---|---|---|---|
| POST | `/api/admin/login` | `{ password }` | `{ token }` |
| GET | `/api/admin/verifications?status=pending` | - | `[{ id, name, org, documentUrl, submittedAt }]` — `documentUrl`은 서류 파일 다운로드/미리보기 링크(선택) |
| POST | `/api/admin/verifications/:verificationId/respond` | `{ decision: "approve" \| "reject" }` | - |

### [MVP 임시 조치] 백엔드 로그인 API 없이 먼저 써보기
`POST /api/admin/login`이 아직 없어도 관리자 화면 접속 자체는 바로 테스트할 수 있게 해뒀습니다. `.env`에 `REACT_APP_ADMIN_PASSWORD`를 설정해두면, 프론트가 서버를 호출하지 않고 **그 값과 직접 비교해서** 로그인시켜줍니다(`src/api/adminVerifications.js`의 `adminLogin`).

```
REACT_APP_ADMIN_PASSWORD=원하는_임시비밀번호
```

- 로그인만 이 방식으로 통과하고, 그 이후 목록 조회(`GET /api/admin/verifications`)·승인/반려는 여전히 실제 백엔드 API를 호출합니다. 백엔드가 없으면 그 부분은 에러 문구로 보이는 게 정상입니다.
- **`POST /api/admin/login`을 실제로 구현하면 `.env`에서 이 줄을 지우세요.** 그러면 코드 수정 없이 자동으로 서버 로그인 방식으로 전환됩니다.
- 이 값은 정말 임시용입니다 — 프론트 번들에 그대로 노출되는 값이라 공모전 심사/데모 이후에는 반드시 지우고 실제 백엔드 로그인으로 넘어가야 합니다.

`respond` 처리 시, 해당 신청과 연결된 사용자의 `GET /api/verifications/me` 결과가 승인이면 `{ verified: true, status: "approved" }`, 반려면 `{ verified: false, status: "rejected" }`로 바뀌도록 백엔드에서 함께 갱신해주세요 — 그래야 사용자 쪽 마이페이지에도 반영됩니다.

### 보안 관련 참고
- 지금은 **비밀번호 하나로 로그인하는 가장 단순한 방식**입니다. 실제 운영 전에는 관리자 계정을 여러 명이 나눠 쓸 경우 계정별 아이디/비밀번호로, 그리고 `POST /api/admin/login`은 반드시 HTTPS로만 호출되도록 해주세요.
- 관리자 API(`/api/admin/*`)는 프론트가 보내는 토큰이 실제로 유효한 관리자 토큰인지 백엔드에서 반드시 검증해야 합니다 — 프론트의 라우트 분리는 UX 편의일 뿐, 인증/인가는 전적으로 백엔드 책임입니다.
- 서류 파일은 아무나 접근 못 하도록(예: 서명된 임시 URL) 제공하는 것을 권장합니다.
